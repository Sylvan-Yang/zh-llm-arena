# 🧠 设计取舍与辩护（Design Decisions）

> 这份文档是给**面试**准备的：当面试官问“你为什么这么设计”，下面每一条都是一个能讲清楚的点。
> 结论先行：我们不是复刻 Chatbot Arena，而是把一套成熟方法论**本地化迁移到一个服务不足的中文市场**。

---

## 1. 为什么用 Elo，而不是单纯算“胜率”？

**胜率的问题**：胜率会被“对手强弱”污染。一个模型一直跟弱手打，胜率虚高；跟强者打，胜率虚低。跨题目、跨对手时不可比。

**Elo 的解决**：每场按双方当前分数算“期望胜率”，赢强者涨分多、赢菜鸟涨分少。最终结果是一个**可跨题目比较的绝对分数**（初始均 1500），天然把对手强度算进去了。

> 一句话面试版：Elo 让“赢了谁”也参与计分，所以两个模型的分数能直接比高低，而胜率只能看“赢了多少场”。

## 2. 为什么保留“平手 / 都差”这个选项？

很多盲测只让选 A 或 B，会**强迫用户二选一**，在两者确实半斤八两时引入噪声。我们加“平手/都差”：

- 尊重真实体验（有些题两个模型都拉胯，或都挺好）；
- 在 Elo 里平手记为 0.5 / 0.5，分数不漂移，符合直觉；
- 还能顺带统计“都差率”，作为题目质量（区分度）的探针。

## 3. 为什么第一版用“静态 mock 回答”而不是直接接 API？

**先用 mock 跑通闭环**，再谈自动化。理由：

- 不依赖任何 API key / 网络 / 费用，第一天就能演示完整产品；
- 把“产品逻辑”（盲测 → 收票 → 算分 → 榜单）和“数据来源”（API）解耦，结构上换数据源不伤骨架；
- 真接 API 时，只需把 `SEED_ANSWERS` 的来源从“手动粘贴”换成“代码生成”，界面与算法一行都不用改。

## 4. 为什么用 Streamlit + 本地 CSV，而不是 React + Supabase？

针对**产品实习生求职**这个场景做的取舍：

- **Streamlit**：纯 Python 写界面，零前端基础也能跑、能改、能讲；先把“能演示”拿到手。
- **本地 CSV**：单人/小样本阶段，CSV 够用、零运维；避免一上来就被数据库吓住。
- **Supabase 推迟到“真有多人用”时**：多人并发、防作弊、跨设备才需要数据库。过早上基础设施 = 为不存在的需求加班。

> 面试版：技术选型服务于目标用户和当前阶段，而不是“用最潮的”。先验证闭环，再按真实负载升级。

## 5. LLM-as-Judge 为什么是“可选补充”而不是“主裁判”？

- 人工盲测代表**真实用户体验**（我们的核心主张）；
- 自动裁判（LLM-as-Judge）可作为**规模化补充**和交叉验证，但裁判模型自身也有偏见（位置偏见、长度偏见、自我偏好）。
- 防偏见要点（写裁判 prompt 时要注意）：
  - **匿名 + 随机左右**，避免位置偏见；
  - **明确判分维度**（正确性/有用性/表达/指令遵循），避免“越长越好”；
  - **让裁判说明理由**，便于人工抽检偏差。

## 6. 为什么是“6 类 × 5 条 = 30 条”这类结构，而不是一个大杂烩？

- **分类**让榜单能看“偏科”（写作强但数学弱），对产品/用户更有洞察；
- **每类 易/中/难 分布**，保证题目有区分度，不会出现“全送分”或“全劝退”；
- **版本号管理**（v1 → v2），保证历史投票数据可复现、可对比。
